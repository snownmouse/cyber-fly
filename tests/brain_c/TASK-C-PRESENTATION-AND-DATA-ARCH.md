## 0. 先更正一处我上一轮的错判

**上一轮我说"板子没有摄像头、没有光敏传感器"—— 错了，而且错得不小。**

我只查了**板载器件**，漏掉了 **ESP-Mosaico 的两个扩展槽（subboard）**。BSP 里明确有：

|---|---|---|
| `mosaico_module_camera` | **OV3640 / SC101IOT DVP 相机**（含硬件 JPEG 解码） | **仅左槽** |
| `mosaico_module_interact` | 触/键、运动、**光**、WS2812、红外 | 左或右 |

⇒ **视觉和光敏都是官方扩展模块**，是"还没插"，不是"用不了"。你说得对。

**仍然没有的**：气味、味觉、温度、湿度（`ORN/OLFA`、`SUGAR/BITTER`、`THERMO/HYGRO`）。

**两条硬约束**（会进方案）：

2. **视觉不是接上就灵**：作者实测"从光感受器驱动 → 下行神经元全 0 Hz"，必须注入 **LC4**；
   且真实像素 → flyvis → LPLC2 这条链在 **45 mm 外读数恒为 0**。按这两条负结果设计。

**作者自己的"它做不到什么"**（很重要，避免我们踩同样的坑）：

| 想做的事 | 实际结果 |
|---|---|
| 从感光细胞驱动行为 | 下行神经元**全 0 Hz**，必须注入 LC4 |

## 2. 三层架构（按你的要求：服务器为主、本地最小、实时同步）

```
┌─────────────────────── 第 1 层：板端（ESP-Mosaico）───────────────────────┐
│  传感器                     本地最小存储                    执行/呈现         │
│  Mic ─→ JO特征 ┐                                     ┌─→ 屏幕(赛博果蝇)     │
│  IMU ─→ 本体感 ├─→ 68B 特征帧 ────┐                  │   480×480           │
│  Touch ────────┘   @20Hz          │                  ├─→ 马达 GPIO8 PWM     │
│  (相机/光感 可选)                  │                  └─→ LED / 状态        │
│                                   │                                        │
│  本地只留：NVS 配置 + 最近 60 s 环形缓冲（≈82 KB）+ 服务器下发的脑参数      │
└───────────────────────────────────┬────────────────────────────────────────┘
                    上行 68 B @20Hz  │  ▲  下行命令 ~12 B @20Hz
                    (Wi-Fi 6 / UDP)  │  │
┌───────────────────────────────────▼──┴────────────────────────────────────┐
│              第 2 层：云服务器（Lighthouse，唯一权威数据源）                │
│                                                                            │
│  UDP 收发器 ─→ 特征解码 ─→ 刺激编码(JO/TOUCH/…) ─→ 脑引擎(flywire-fly-lab) │
│       │                                                    │               │
│       │                                             读出 DN ─→ 运动指令    │
│       └──────────────→ 追加写：原始特征 / 读出 / 会话元数据（只增不改）      │
│                        脑状态检查点 · 旋转压缩 · 断连回放                   │
│                                                                            │
│  对外：WebSocket / SSE 推送「状态向量」（不是像素）→ 第三方查看器           │
└───────────────────────────────────┬────────────────────────────────────────┘
                                    │  状态向量 @20 Hz（几十字节）
┌───────────────────────────────────▼────────────────────────────────────────┐
│              第 3 层：呈现（网页 / 你的电脑）                                │
│  · 实时看板：脑活动、读出速率、延迟、情感/能量、那只果蝇的动画              │
│  · 历史回放：任意时段重放（数据在服务器，本地不落盘）                        │
└────────────────────────────────────────────────────────────────────────────┘
```

设计要点：**板上不做重活，云端不做慢活，呈现层不做算**。

## 3. 数据架构细则（对应你的四条要求）

| 你的要求 | 落地方案 | 依据 |
|---|---|---|
| **数据主体存服务器** | 服务器为**唯一权威源**：原始特征帧、读出、会话元数据**只增不改**（append-only），按天/会话分文件，压缩归档 | 已有 `udp_probe_server.py` 与 `/root/probe.log` 先例 |
| **本地只存少部分** | 板上只用：**NVS**（Wi-Fi/标定/会话号/脑参数）+ **最近 60 s 环形缓冲**（20 Hz × 68 B × 60 ≈ **82 KB**，NAND 上九牛一毛） | 板有 16 MB QSPI Flash + **SPI NAND** + PSRAM 250 MHz，但**故意不用满** |
| **本地 ↔ 服务器实时更新** | 上行 20 Hz 特征帧、下行 20 Hz 命令帧，**这条链任务 A 已实测 0.5% 丢包**；断连时板上环形缓冲**补传**，服务器按时间戳去重 | 任务 A 实测：稳态 0.00%、burst 0.50%、RTT avg 66 ms |
| **本地不预存太多数据** | 板上**不存历史会话、不存脑权重、不存图像**；一切都按需从服务器取；固件保持小、启动快 | 也让"本地运行更方便" |

**为什么这样切**：
- 我们**唯一不能省的是延迟**。把数据留在本地只会让两侧状态分叉；**单一权威源**才能保证
  "你在网页上看到的"和"板上那只果蝇感受到的"是**同一份**状态。
- 板上存得越少，**固件越稳、OTA 越快、恢复越简单**（任务 A 已经吃过 BSP/OTA 的苦）。

**呈现层为什么推"状态向量"而不是视频流**：
- 20 Hz、几十字节的状态向量，**带宽和延迟都可忽略**；推像素则要 ~几十 MB/s，得不偿失。
- 板端 480×480 的动画**本地渲染**（raylib-lite 现成），云端只发"它现在什么心情/什么动作"。

## 4. "赛博果蝇"呈现设计

### 4.1 板端屏幕（480×480，本地渲染）

**不要从零做。** 仓库里已经有**完整的虚拟宠物渲染栈**可以直接改：

| 现成件 | 路径 | 作用 |
|---|---|---|
| Raylib-lite 引擎 | `submodule/raylib-lite-engine` | RGB565 2D 渲染、固定步长、精灵/图集/粒子、Scene/UI |
| 虚拟宠物（最佳模板） | `projects/desktop_pet/main/pet_*.c` | `pet_game.c`(逻辑，可 PC 编译) + `pet_view.c`(渲染) |
| **屏幕镜像到主机** | `projects/desktop_pet/main/pet_screen_mirror.c` | **正是"本地/服务器实时看到板端画面"的现成件** |
| PC 端模拟器 | `game.sim.json` + `python3 mosaico.py game sim projects/<name>` | **本地就能看 480×480 效果**，不用刷板 |
| 参考游戏 | `projects/raylib_shooter`、`tower_defense`、`sky_hop` | 手感/性能/资源管线的范例 |

**屏幕内容（第一版）**：把 `desktop_pet` 的"心/饱/精力"换成**脑的真实状态**：

| 屏上元素 | 来源（服务器下发） |
|---|---|
| 果蝇的身体姿态、朝向 | `DNa01/DNa02`（转向）、`MDN`（后退） |
| 翅膀/抖动强度 | 马达强度回显 + 逃逸标志 `DNp01` |
| 眼睛/触角的反应 | `JO` 通道活跃度（麦克风听到的） |
| "心情/警觉"条 | 读出神经元群体速率（不是手写的假变量） |
| 角落小字 | Wi-Fi 信号、RTT、丢包、脑步耗时（调试用，可关） |

**关键原则**：屏幕上每一个会动的元素都要**来自脑的输出**，不做"装饰性动画"。
否则它就只是电子宠物，不是"这个大脑的窗口"。

### 4.2 服务器端（你说的"我会调出来看"）

**直接沿用仓库自己的网页呈现**，不另起炉灶：

- `results/dodge/fly_dodge.html` —— 现成的**实时大脑游戏页**（Node 引擎 + 网页前端），
  把它从"躲避球"改成"显示我们这 68 字节特征驱动的脑"。
- `docs/ecobox.html` —— 生态箱呈现范式（世界 + 脑表面 + 学习曲线）。
- `viz/lplc2_replay.template.html` —— 视觉回放范式（装了相机后用）。
- 数据接口：服务器加一个 **WebSocket/SSE**，把「状态向量」推给网页；**网页不读板，只读服务器**。

### 4.3 本地开发怎么看

- **不刷板就能看**：`python3 mosaico.py game sim projects/<name>`（Host 模拟器）出 RGB565 预览。
- **板上真实画面**：`pet_screen_mirror` 那条路（注册后把板端帧镜像到主机）。
- 这样"本地 ↔ 服务器"是**同一份状态的两个视图**，不是两套实现。

## 5. 关于"学习 / 平衡学习 / 蘑菇体"的诚实判断

你的直觉方向我认真查了。结论分三层，**都要如实说**：

### 5.1 蘑菇体（MB）现在**仍然不上** —— 理由不变

- **输入是嗅觉**（`ORN` 2,279 个），我们**没有气味传感器**。
- **记忆走不到马达**：作者实测有运动落点的四类 MBON **一个脉冲都没有**（APL 抑制是 KC 兴奋的 2–7 倍）。
- **奖赏是手接的线**：真喂糖，PAM 多巴胺 **0/307 放电**。
- **吃掉全部余量**：实时 **2.82× → 0.96×**。

⇒ 就算现在硬接，也**出不来动作**。**光敏传感器也救不了它**（MB 不收光感输入）。

### 5.2 但"学习"这件事，在这个项目里**有另一条真能走通的路** —— 不在连接组里

这是我这轮读出来的关键：作者在 `eco/`（生态箱）里实现了**连接组之外的一层可塑性**，
并且**记录到它真的学会了**：

> 生态箱学成的个体搬进 3D 大自然：**喝得更久 5/5、更不渴 5/5**。

⇒ **"让机器人学会点什么"是可行的，路径是"脑读出 + 外部可塑性层"，而不是"指望连接组自己学会"。**
这恰好回答你"平衡学习这类可以考虑"——**可以，但要用 eco 那套外挂可塑性的思路，不要指望 MB。**

### 5.3 所以"平衡"应该怎么做（建议）

- **平衡本身**：优先用**板端快反射 + 云端读出**做闭环（`DNa` 转向、`MDN` 后退、`vnc/` 的本体感觉闭环）。
  果蝇本来就不靠"学习"维持平衡，靠的是反射 + 本体感觉，**生物学上也对**。
- **"学习平衡"**：作为**第三期**，用 `eco/` 的可塑性层范式，把"平衡误差"当奖励信号，
  但**放在连接组外面**（就像作者做的那样）。**不要**把它塞进 MB。
- **门留着**：哪天真加了气味传感器（廉价 MOX 即可），`plasticity.js` 现成，MB 直接能用。
